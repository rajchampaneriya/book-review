# Experiment 3 (MVP): a retry is not a resend

## Question

When the response to a committed booking is lost and the client retries, does the service
create a second booking and a second charge? Compare a naive POST with an idempotency-keyed
POST, built identically in three stacks.

## Stacks

| Stack | Path | Framework and data access | Host port | NodePort | DB schema |
| --- | --- | --- | --- | --- | --- |
| dotnet | stacks/dotnet | .NET 10 minimal API, Npgsql, no ORM | 8081 | 30081 | dotnet |
| java | stacks/java | Spring Boot 4.1.x on Java 25, Spring MVC, JdbcClient, HikariCP | 8082 | 30082 | java |
| python | stacks/python | Python 3.14, FastAPI, Uvicorn, an async Postgres driver with 3.14 wheels | 8083 | 30083 | python |

- Every service listens on port 8080 inside its container; its NodePort Service maps the host port to it.
- Plain SQL in every stack (no ORM), so database behaviour is identical and readable.
- Each service: requests cpu 1, limits cpu 2 and memory 1Gi.
- Database pool: 20 connections per service in total (Python: 2 Uvicorn workers x 10).
- Java keeps the default platform-thread Tomcat for this experiment; virtual threads belong to post 2.
- Record any deviation, and every exact version, in `versions.md`.

## Data model (`db/schema.sql`, applied once per stack schema)

```sql
CREATE SCHEMA IF NOT EXISTS {stack};

CREATE TABLE {stack}.bookings (
  id            uuid PRIMARY KEY,
  client_ref    text NOT NULL,       -- measurement only; deliberately NOT unique
  session_id    text NOT NULL,
  dog_id        text NOT NULL,
  owner_id      text NOT NULL,
  deposit_cents integer NOT NULL CHECK (deposit_cents > 0),
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE {stack}.charges (
  id           uuid PRIMARY KEY,
  booking_id   uuid NOT NULL REFERENCES {stack}.bookings(id),
  client_ref   text NOT NULL,
  amount_cents integer NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE {stack}.idempotency_keys (
  key          text PRIMARY KEY,
  request_hash text NOT NULL,
  result       jsonb,                -- the use case's result: booking_id, charge_id, status
  created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX ON {stack}.bookings (client_ref);
CREATE INDEX ON {stack}.charges (client_ref);
```

`client_ref` exists only so the harness can count duplicates. It is not an idempotency
mechanism and must never get a unique constraint. Charges are simulated rows; never call a
payment provider. IDs are generated by the application (UUID v4 or v7).

## HTTP contract (identical in every stack)

Request body, JSON, all fields required, unknown fields rejected:

```json
{ "client_ref": "r1-000123", "session_id": "s-42", "dog_id": "d-7", "owner_id": "o-9", "deposit_cents": 2500 }
```

- Invalid body: `400 {"error":"invalid_request"}`.
- `GET /health`: `200 {"status":"ok","stack":"<stack>"}`.

### `POST /naive/bookings` (intentionally naive baseline)

1. One transaction: insert the booking, insert the charge (amount = deposit_cents), commit.
2. Fault hook (below).
3. `201 {"booking_id":"…","charge_id":"…","status":"confirmed"}`.

No key, no deduplication, no retries, no locks.

### `POST /v2/bookings` (idempotency-keyed)

- Header `Idempotency-Key` is required: 1 to 255 printable ASCII characters. Missing or invalid:
  `400 {"error":"idempotency_key_required"}`.
- `request_hash` = lowercase hex SHA-256 of the UTF-8 string
  `client_ref + "\n" + session_id + "\n" + dog_id + "\n" + owner_id + "\n" + deposit_cents` (decimal).
- `BookSessionIdempotentService` (application layer, behind the `BookSessionIdempotentUseCase` /
  `IBookSessionIdempotent` driving port) does this through the `BookingStore` driven port, in one transaction:
  1. Claim the key: the Postgres adapter runs `INSERT INTO idempotency_keys (key, request_hash) VALUES ($1, $2)`.
     On a unique violation (SQLSTATE 23505) the adapter rolls back and raises the application-level
     key-already-claimed error defined with the driven port (`KeyAlreadyClaimedError` in Python,
     `KeyAlreadyClaimedException` in Java and .NET). No driver exception crosses the port.
  2. Otherwise create the booking and the charge, store the result (booking_id, charge_id, status) in
     the key row, and commit.
  3. On that error, read the key row through `BookingStore.find_key`, outside the failed transaction:
     - Hash differs: the use case returns `Conflict`; the HTTP adapter maps it to
       `422 {"error":"idempotency_conflict"}`.
     - Result present: the use case returns `Replayed(result)`; the HTTP adapter maps it to `201` with
       the same body and header `Idempotent-Replayed: true`.
     - Result missing (should be impossible after a commit): `InFlight`, mapped to
       `409 {"error":"idempotency_in_flight"}` with `Retry-After: 1`, and logged as a bug.
- Fault hook, then `201` with the body.

A concurrent duplicate blocks on step 1 until the first transaction commits, then takes the replay
path. The contract tests check this. The application layer owns the policy and the request hash;
it never sees SQL, HTTP status codes or framework types.

## Fault hook (both variants)

- It is a transport concern, so it lives in the inbound HTTP adapter: the route calls it after the
  use case has returned (the commit has happened) and before the response is written. Bootstrap
  passes it the configuration.
- Active only when env `FAULT_INJECTION=enabled`. Otherwise it is a no-op.
- When a request carries header `X-Fault: hold-after-commit`, wait `FAULT_HOLD_MS` (default 2000)
  after the commit and before writing the response. Use the stack's non-blocking wait where it has one
  (`await asyncio.sleep`, `await Task.Delay`); Java uses `Thread.sleep`.
- The client timeout is 1000 ms, so the client sees a timeout for a booking that is already committed.
- The load script decides which requests carry the header, so the same logical requests are faulted
  in every stack and every run.

## Load (`harness/k6/exp3.js`)

- Env: `BASE_URL`, `STACK`, `VARIANT` (naive or v2), `FAULT_RATE` (0, 0.01, 0.05), `RUN_ID`,
  `RATE` (default 100 per second), `TOTAL` (default 10000), `TIMEOUT` (default 1s),
  `MAX_ATTEMPTS` (default 3), `BACKOFF_MS` (default 200).
- Executor: `constant-arrival-rate`, duration = TOTAL / RATE seconds, enough VUs that
  `dropped_iterations` is 0. Record it anyway.
- Logical request `i` = `exec.scenario.iterationInTest`. `client_ref` = `${RUN_ID}-${i}`.
  For v2, `Idempotency-Key` = the same value.
- Request `i` is faulted if `((i * 2654435761) % 10000) < FAULT_RATE * 10000`, on its first attempt only.
- Retry on status 0 (timeout or network error) and on 5xx, with the same body and key, up to
  `MAX_ATTEMPTS` attempts in total, sleeping `BACKOFF_MS` between attempts. Retry 409 in-flight;
  do not retry other 4xx.
- Custom metrics: `logical_requests`, `attempts`, `timeouts`, `gave_up`, and latency of successful
  attempts. `handleSummary` writes `results/exp3/raw/<stack>_<variant>_f<fault>_r<run>.json`, which is
  committed with the results as evidence.

## Measurement

- Before each run, truncate the stack's three tables.
- After each run, query the stack's schema:
  - `duplicate_bookings` = bookings_total - count(distinct client_ref) in bookings
  - `duplicate_charges` = charges_total - count(distinct client_ref) in charges
  - `lost` = logical_requests - count(distinct client_ref) in bookings
- Duplicates are always counted in the database, never inferred from client logs.

## Run matrix (`make exp3-all`)

- 3 stacks x 2 variants x FAULT_RATE {0, 0.01, 0.05} x 3 runs = 54 runs, about 100 s each at the defaults.
- Before a stack's first run: 60 s warm-up at RATE with FAULT_RATE=0, not measured.
- Only the stack under test receives load; scale the other stacks to 0 replicas.
- Resumable: skip runs already present in runs.csv for the same git SHA.
- `DRY_RUN=1` prints the planned runs and the estimated duration without running anything.

## Output files

- `results/exp3/runs.csv`, one row per run: timestamp_utc, stack, variant, fault_rate, run, rate,
  logical_requests, attempts, timeouts, gave_up, dropped_iterations, bookings_total,
  duplicate_bookings, duplicate_charges, lost, p50_ms, p95_ms, p99_ms, git_sha.
- `results/exp3/host.json`: OS, CPU model and cores, memory, Docker Desktop or Podman version,
  k3d, kubectl and k6 versions. Captured once per `make exp3-all`.
- `results/exp3/summary.csv`, one row per (stack, variant, fault_rate): median and min-max over runs of
  duplicate_bookings, duplicate_charges and lost; `duplicates_per_10k` = duplicate_bookings /
  logical_requests x 10000; and, at fault 0, p99 overhead = median p99 (v2) - median p99 (naive).

## Chart (`figures/exp3_duplicates.py` writes `figures/exp3_duplicates.svg`)

- Reads `results/exp3/summary.csv` only.
- Grouped bars: one group per stack; within each group four bars: 1% naive, 1% keyed, 5% naive,
  5% keyed. y = duplicate bookings per 10,000 logical requests (median of three runs), with a thin
  whisker for the min-max of the runs.
- Colours: naive `#1F4E79`, keyed `#9DB9D5`. Print the value above every bar, including 0.
- Transparent background, text `#555555`, no gridline clutter, readable on light and dark pages.
- Title is a placeholder, `TITLE: author to write`. The author writes it after reading the data.
- Arguments: `--input` (default `results/exp3/summary.csv`) and `--output` (default `figures/exp3_duplicates.svg`).
- `figures/tests/test_exp3_duplicates.py` runs the script as a subprocess on the labelled synthetic
  fixture `figures/tests/fixtures/exp3_summary_synthetic.csv`, writing into `tmp_path`, never touching `results/`.

## Contract tests (`contracts/tests`, pytest and httpx; `make contract STACK=<stack>`)

1. `/health` returns the stack name.
2. Naive: two identical POSTs create two bookings (proves the baseline is naive).
3. v2: a missing key returns 400 `idempotency_key_required`.
4. v2: the same key and body twice create one booking; the second response is 201, has
   `Idempotent-Replayed: true` and the same body.
5. v2: the same key with a different body returns 422 `idempotency_conflict`.
6. v2: 20 concurrent requests with the same key and body create exactly one booking and one charge;
   every response is 201 with the same booking_id.
7. Both: an invalid body returns 400 `invalid_request`.
8. The fault hook is off by default: a request with `X-Fault` but without `FAULT_INJECTION=enabled`
   responds in under 500 ms.

Tests count rows in the database directly, at `localhost:55432` (see Infrastructure), in the schema
named after the stack, with the local-development credentials from `infra/k8s/postgres.yaml`.

## Infrastructure (`infra/`)

- k3d cluster `wcf-physics` (k3s inside Docker or Podman), one server node, defined in
  `infra/k3d/cluster.yaml`. Host ports 8081-8083 map to NodePorts 30081-30083 (dotnet, java, python)
  and host port 55432 maps to NodePort 30432 (Postgres).
- Postgres: the current major version (verify the image tag), one pod, disposable storage, credentials
  in a Secret labelled as local-development defaults. `infra/scripts/apply-schema.sh` renders
  `db/schema.sql` once per stack schema.
- The contract tests and the harness reach Postgres at `localhost:55432` from the host. Nothing needs a
  port-forward or `kubectl exec`.
- Builds and tests run in containers. Each stack's Dockerfile has four stages: `build`, `unit` (runs
  the unit tests), `arch` (runs the architecture tests) and `runtime` (the deployed image).
  `make unit` and `make arch` build their stage with `$(ENGINE) build --target <stage>`, so a failing
  test fails the build. `make deploy` builds `runtime`, tags it `wcf-physics/<stack>:dev`, loads it
  with `k3d image import` and restarts the Deployment. `ENGINE` is `docker` or `podman`, detected by
  the Makefile and overridable.
- Host prerequisites, all checked and printed by `make doctor`: Docker Desktop or Podman, k3d,
  kubectl, k6, jq and Python 3.12 or later. The host Python runs only the hooks, `tools/arch`, the
  contract tests, the harness and the chart, from `.venv` built from `requirements-host.txt`. The host
  needs no JDK, .NET SDK or Python 3.14.
- `make up` must work from a clean machine with only those prerequisites.
- Podman: k3d needs the Podman socket and `DOCKER_HOST` set. If k3d fails on Podman on this machine,
  stop and report; do not switch to docker compose without approval.

## Architecture tests (`make arch STACK=<stack>`)

`make arch` runs two checks and fails if either fails:

1. `python3 tools/arch/check_hexagonal.py <stack>` on the host: the shared static checker. It checks
   that every file listed for the stack in the CLAUDE.md tree exists and no other file does, then
   layout, naming conventions, folders against packages and namespaces, module and project
   references, imports, fully qualified names, frameworks in the core, and that the stack's
   architecture test is an unmodified copy of its template.
2. The stack's own architecture tests, copied verbatim from `tools/arch/templates/` (protected), run
   in the Dockerfile stage `arch`:

| Stack | Template | Copy to | Command in stage `arch` |
| --- | --- | --- | --- |
| python | `python/importlinter.toml` (5 contracts) | `stacks/python/importlinter.toml` | `lint-imports --config ../importlinter.toml` from `src/` |
| java | `java/HexagonalArchitectureTest.java` (ArchUnit, 5 rules) | `booking-bootstrap/src/test/java/work/rajc/booking/architecture/` | `mvn -B -pl booking-bootstrap -am test -Dtest=HexagonalArchitectureTest -Dsurefire.failIfNoSpecifiedTests=false` (needs test-scoped `archunit-junit5`) |
| dotnet | `dotnet/HexagonalArchitectureTests.cs` (NetArchTest, 6 facts) | `tests/Rajc.Bookings.ArchitectureTests/` | `dotnet test tests/Rajc.Bookings.ArchitectureTests` (needs `NetArchTest.Rules` and xunit) |

All three encode the same rules: dependencies point inward; adapters never depend on each other or
on application services; ports never depend on services; domain and application use no frameworks
or drivers. Package versions for ArchUnit, NetArchTest and xunit are chosen at build time, verified
from the registries and recorded in `versions.md`.

Each stack's architecture tests must be shown to fail before they are trusted: add one deliberate
violation (for example, the application layer importing the Postgres adapter), run `make arch`,
show the failure, revert, show the pass, and say so in the commit message. If a template does not
compile or run, stop and tell the author; do not edit it or work around it.

## MVP acceptance

- `make doctor && make up` work on a clean machine; `make contract` passes for every stack.
- `make exp3 STACK=python VARIANT=naive FAULT=0.05 RUN=1` appends one row to runs.csv.
- `make exp3-all`, `make summary` and `make chart` produce the files above with no hand edits.
- `make arch` passes for every stack, and each stack's architecture tests were shown failing on a deliberate violation first.
- `python3 tools/arch/check_hexagonal.py --all --complete` passes: every file in the CLAUDE.md tree exists and nothing else does.
- `versions.md` lists every runtime, framework, driver and image tag actually used.
